# Evals do plugin data-engineering

Status: **designed_not_executed**. Os 16 casos foram desenhados em 2026-10-10 (13 a partir do `SYNTHESIS.md` do segmento, seção 4.9, e 3 acrescentados pela validação de qualidade para cobrir backfill e os agentes `data-pipeline-reviewer` e `eval-judge`) e não foram executados. Nenhum resultado, taxa de acerto ou ganho sobre o baseline pode ser alegado a partir desta pasta. A qualidade do plugin foi avaliada por leitura e por revisão de modelos da mesma família, o que não equivale a medição. O Claude Code da máquina de construção (2.1.128) é anterior ao mínimo exigido por `claude plugin eval` (2.1.269).

## Como rodar

Requisito: Claude Code 2.1.269 ou superior (`claude --version`). Nessa instalação a pasta pode ser validada de forma estrutural com `python tools/verify_plugin.py plugins/data-engineering` e `claude plugin validate`, que não executam os casos.

```bash
cd plugins/data-engineering
claude plugin eval .
claude plugin eval . --ablation with-without   # padrão por caso; compara com o baseline sem o plugin
claude plugin eval . --ablation none --runs 1   # um braço, uma execução, para iterar nos graders (conferido na documentação em 2026-10-10)
```

- Rode com **somente este plugin carregado**. O regex dos graders de disparo aceita nomes de skill sem prefixo (`playbook`, `prompts`), então um plugin homônimo instalado também satisfaria `skill-fired` e quebraria `no-plugin-skill` sem culpa deste plugin.
- Cada caso declara `runs: 3`. Uma execução não prova nada; olhe a consistência entre as três (pass^k), não só se alguma passou (pass@k).
- Custo: 16 casos x 3 execuções = 48 execuções, o dobro com ablação. Os casos têm `max_turns: 12` e `timeout_seconds: 600`. Não há estimativa de tokens verificada; meça na primeira rodada e ajuste `runs`, `max_turns` e `timeout_seconds`.
- Os casos `pedido-destrutivo-em-producao`, `keyword-em-yaml-nao-ativa-modo-completo` e `upgrade-dbt-main-arvore-suja` listam `Bash`, `Write` e `Edit` em `allowed_tools` para declarar que medem restrição de ações. Conferido em 2026-10-10 na documentação do `claude plugin eval` (https://code.claude.com/docs/en/plugin-evals): `allowed_tools` só concede ferramentas de leitura; `Bash`, `Write` e `Edit` são removidos da sessão a menos que você os conceda com `--allow-tools`. Sem a concessão, os graders `no-exec`, `no-write` e `no-edit` passam sem medir nada, porque o modelo não consegue chamar a ferramenta. Para medir de verdade, rode esses três casos com `claude plugin eval . --case pedido-destrutivo-em-producao --allow-tools Write Edit Bash` (e analogamente para os outros dois). Com `Bash` concedido, cada comando roda no sandbox do sistema operacional, que a documentação diz não existir no Windows nativo: use WSL2 ou Linux. O workspace é vazio e descartável; não use um repositório ou um warehouse real. Os graders supõem que o runner compara o regex com a entrada serializada em JSON (campos `command` e `file_path`); confirme na primeira rodada que uma chamada proibida de teste é detectada.
- `no-references-read` do caso 10 usa `min: 0` e `max: 3` (o `min` padrão de `tool_used` é 1, então sem `min: 0` o grader reprovaria quem não lê nenhuma referência). O teto 3 é Suposição: o playbook pode ler uma ou duas referências para responder a pergunta pontual; ler mais de três indica o modo completo. Ajuste depois da primeira rodada.
- Resultados vão para `evals/results/`, ignorado pelo `.gitignore`.

## Como interpretar

- Graders `tool_used` são determinísticos e valem mais que os `llm`, com uma exceção documentada: em execução de dois braços (com e sem plugin), todo `tool_used` sobre `Skill` fica fora da nota e aparece só como indicador de disparo, porque não poderia passar sem o plugin. O grader negativo `no-plugin-skill` usa `arm: both` para ser pontuado nos dois braços. Os `llm` seguem o formato PASS if / FAIL if com itens observáveis, mas o juiz é um modelo da mesma família do executor: calibre contra leitura humana de algumas execuções e leia os transcripts antes de confiar na nota. Rode os graders `llm` fora do contexto do executor, com modelo de outra família quando possível, e desconfie de 100% de aprovação (V-06).
- Falha de disparo é falha da `description`, não do corpo da skill: corrija a descrição antes de mexer no corpo. As skills `pipeline-acceptance` e `gated-pipeline-migration` têm `disable-model-invocation: true`; por isso os casos 2 e 12 medem o comportamento do `playbook` e não o disparo delas.
- Os critérios apoiam-se em fatos conferidos em 2026-10-10 a partir de `VALIDATED.md` (V-05, V-13, V-16, V-17, V-18, V-19, V-20, V-22, V-23, V-25, V-26): `LIMIT` e bytes lidos no BigQuery, `NOT IN` e NULL, garantias de entrega do Flink (documentação do branch master), regras de DAG do Airflow (stable 3.3.2), ODCS 3.2.0. Reconfira as fontes antes de tratar uma falha como erro do modelo.
- Um critério que premie afirmação errada é defeito do eval. Cuidados já tomados: o caso 5 não exige nome de classe de conector (o nome na versão instalada é Não verificado); o caso 3 exige a versão do Airflow como pergunta, porque o padrão de `catchup` e as importações dependem dela; o caso 11 não exige nomes de chave YAML do ODCS, só a versão fixada, a estrutura e a ausência de alegação de validade.
- O caso 2 usa números fictícios inspirados no padrão de falha descrito por um praticante (V-05, classe B, um projeto); não os cite como resultado de benchmark.

## Cobertura conhecida como incompleta

- Os agentes `pipeline-debugger` e `data-pipeline-architect` não têm caso próprio; `analytics-reviewer` é exercitado pelo fluxo principal no caso `metrica-fan-out-count-distinct`. Os casos `revisor-diff-sem-oraculo` e `juiz-criterio-composto` listam `Agent` em `allowed_tools` e usam graders `tool_used` sobre `Agent` com `arm: with-only` (a documentação do `claude plugin eval` diz que um caso com `Agent` pode despachar agentes do plugin pelo nome com namespace, como `data-engineering:data-pipeline-reviewer`; confirme na primeira rodada o formato do campo no JSON da chamada, pois o regex só procura o nome do agente). Próximos candidatos: `data-pipeline-architect` em modo sem interação (plano em rascunho com decisões pendentes) e `pipeline-debugger` com log truncado (causa não confirmada).
- Sem caso para Dagster, Prefect, dbt incremental e snapshots, Delta (`OPTIMIZE`, `VACUUM`), nem para temas em lacuna de fonte (observabilidade de dados, BI, Snowflake, Redshift, Iceberg, Great Expectations e Soda).
- Não há caso de origem de dado em app mobile ou web (eventos atrasados, duplicados e bloqueados); candidato para a próxima rodada, com remissão ao plugin certo.
- Evals de execução sem interação (modo em lote) só são cobertos de forma indireta.
